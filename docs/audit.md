# Разбор кода: ошибки и слабые места

Ссылки на строки соответствуют состоянию репозитория после очистки. Разделы
1 и 2 — то, что уже исправлено; раздел 3 — то, что требует серверной части или
отдельной работы.

## 2. Изменения структуры

| Было | Стало |
|---|---|
| `family-data.js` — данные и логика в одном файле | Только логика: загрузка (`loadArchive`, `whenReady`), запись (`apiSubmitEdit`, `apiModerate`, `apiLogin`), раскладки, парсеры |
| Данные импортировались статически | Единая точка входа: API сервера → иначе `data/sample.json`. Модуль ES — синглтон, поэтому приложение и карта работают с одним набором |
| Адрес сервера нигде не задавался | `config.js` — единственное место конфигурации, без секретов |

## 3. Незакрытое

### 3.1 Требует серверной части

**Скрытие живущих остаётся визуальным.** `app.js:55` — `visible(p)` решает,
показывать карточку, но полные данные уже находятся в браузере гостя. Пока
фильтрация не перенесена на сервер (`docs/deployment.md`, раздел 5, правило 1),
это утечка персональных данных живущих через инструменты разработчика.

**Импорт GEDCOM не выставляет признак `living`.** `family-data.js`,
`parseGedcom`: поле не заполняется никогда, поэтому после импорта настоящего
архива `visible()` вернёт `true` для всех, включая живущих, и гость увидит их
карточки. Требуется правило: отсутствие блока `DEAT` при годе рождения свежее
110 лет → `living: true`, с возможностью ручной отметки модератором. **До
исправления реальный GEDCOM импортировать в публично доступный контур нельзя.**

**Проверка размера и содержимого импорта.** `app.js:214` читает файл любого
размера, `parseJson` принимает любой JSON без проверки структуры: записи с
одинаковыми `id` схлопываются в `byId`, отсутствующие поля роняют раскладку.
Валидация нужна на сервере (лимит 20 МБ, схема, отчёт об отклонённых записях).

### 3.2 Ошибки разбора данных

**Даты GEDCOM не нормализуются.** Проверено на тестовом файле: дата `14 MAR 1902`
попадает в карточку как есть, а `years()` берёт первые четыре символа — в
интерфейсе получается `14 M — 2 NO`. Нужен разбор `DD MMM YYYY`, `ABT/EST/BEF/AFT`
и диапазонов в ISO-форму.

**Многострочные записи теряются.** Теги `CONT` и `CONC` не обрабатываются:
примечание из нескольких строк импортируется пустым.

**Мёртвая ветка.** `family-data.js:269` — `head.events?.FILE?.__val`: поле
`__val` не создаётся нигде, условие всегда ложно и работает только запасной
вариант.

**Зашитый «текущий год».** `family-data.js:236` — `2026` как настоящее время для
живущих. Должно быть `new Date().getFullYear()`.

### 3.3 Ресурсы и производительность

**Утечка объектных ссылок.** `app.js:154` и `app.js:172` создают
`URL.createObjectURL` для каждой фотографии и скана, но `revokeObjectURL` не
вызывается: при разборе папки на 60 файлов память вкладки не освобождается до
перезагрузки. Снимается вместе с переходом на серверное хранение файлов.

**Квадратичная раскладка.** `family-data.js:111` — `kidsOf` фильтрует весь массив
людей для каждого блока. На 50 карточках незаметно, на нескольких тысячах даёт
ощутимую задержку. Лечится предварительным индексом «родитель → дети».

**Печать клонирует канву целиком** для каждого листа. На больших древах операция
тяжёлая и выполняется без индикатора выполнения.

### 3.4 Мелкое

- Флаг `minor` есть в модели, но не влияет ни на видимость, ни на отображение:
  для несовершеннолетних нет отдельного правила доступа.
- Ключи React в галереях и списках фактов заданы индексом массива — при
  пересортировке или удалении состояние элементов смещается.
- Заголовки безопасности (CSP, `X-Content-Type-Options`, `no-store`) задаются
  только на уровне nginx и появятся вместе с развёртыванием.
- `<family-map>` ждёт появления `window.d3` не более 12 секунд и при неудаче
  показывает общее сообщение, не различая отсутствие сети и ошибку SRI.

## 4. Порядок устранения

| Очередь | Пункты | Условие |
|---|---|---|
| До загрузки реальных данных | 3.1 целиком | Иначе персональные данные утекут гостям |
| Вместе с этапом 1 плана | 3.2 | Импорт настоящего GEDCOM без нормализации дат бесполезен |
| Вместе с этапом 4 плана | Утечка объектных ссылок из 3.3 | Снимается переходом на серверное хранение фотографий |
| По мере роста архива | Остальное из 3.3 и 3.4 | Не блокирует запуск |

# Разбор кода: ошибки и слабые места

Разделы 1-3 — то, что уже исправлено: сначала при очистке репозитория, затем
вместе с серверной частью. Раздел 4 — то, что осталось, с указанием, чему это
мешает.

## 1. Устранённые критические

## 2. Изменения структуры

| Было | Стало |
|---|---|
| `family-data.js` — данные и логика в одном файле | Только логика: загрузка (`loadArchive`, `whenReady`), запись (`apiSubmitEdit`, `apiModerate`, `apiLogin`), раскладки, парсеры |
| Данные импортировались статически | Единая точка входа: API сервера → иначе `data/sample.json`. Модуль ES — синглтон, поэтому приложение и карта работают с одним набором |
| Адрес сервера нигде не задавался | `config.js` — единственное место конфигурации, без секретов |

## 3. Закрыто серверной частью

| Что было | Как закрыто |
|---|---|
| **Скрытие живущих визуальное.** `visible()` решал, рисовать ли карточку, но полные данные уже лежали в браузере гостя — утечка через инструменты разработчика | `server/host/archive.js`: записи `living` не попадают в ответ гостю, ссылки на них вычищаются из `parents`/`spouse`. Проверяется в `selftest.js` запросом, а не по интерфейсу |
| **Импорт GEDCOM не выставлял `living`.** После импорта настоящего архива гость увидел бы всех | `guessLiving()` в `family-data.js`: нет `DEAT` и меньше 110 лет → живущий; без обеих дат — тоже живущий. `cli/import.js` печатает поимённый отчёт для проверки модератором |
| **Даты GEDCOM не нормализовались.** `14 MAR 1902` попадало в карточку как есть, в интерфейсе выходило `14 M — 2 NO` | `normalizeDate()` в `family-data.js`: `DD MMM YYYY`, `ABT/EST/CAL/INT/BEF/AFT`, диапазоны `BET…AND`/`FROM…TO` |
| **Зашитый 2026 как «настоящее время»** | `new Date().getFullYear()` в `mapPoints` |
| **Импорт без проверок.** Файл любого размера, дубли `id` схлопывались, отсутствующие поля роняли раскладку | `cli/import.js`: лимит 20 МБ, отсев записей без `id` и имени, дублей и ссылок на несуществующих людей, отчёт об отклонённых |
| **Заголовки безопасности только в планах** | `gen-tree.caddy`: CSP `default-src 'self'`, HSTS, `nosniff`, `Referrer-Policy`. Все ответы API — `no-store` |
| **Зависимости с чужих CDN** | `tools/vendor.sh` кладёт их локально с проверкой SHA-384; посетитель архива не обращается к unpkg и jsdelivr |

## 4. Незакрытое

### 4.1 Ошибки разбора данных

**Многострочные записи теряются.** Теги `CONT` и `CONC` не обрабатываются.
Сейчас безвредно: `parseGedcom` не переносит примечания в карточку вообще —
станет важно, когда `NOTE` начнут импортировать.

**Мёртвая ветка.** `family-data.js`, разбор заголовка GEDCOM —
`head.events?.FILE?.__val`: поле `__val` не создаётся нигде, условие всегда
ложно и работает только запасной вариант.

### 4.2 Ресурсы и производительность

**Утечка объектных ссылок.** `app.js:154` и `app.js:172` создают
`URL.createObjectURL` для каждой фотографии и скана, но `revokeObjectURL` не
вызывается: при разборе папки на 60 файлов память вкладки не освобождается до
перезагрузки. Снимается вместе с переходом на серверное хранение файлов.

**Квадратичная раскладка.** `family-data.js:111` — `kidsOf` фильтрует весь массив
людей для каждого блока. На 50 карточках незаметно, на нескольких тысячах даёт
ощутимую задержку. Лечится предварительным индексом «родитель → дети».

**Печать клонирует канву целиком** для каждого листа. На больших древах операция
тяжёлая и выполняется без индикатора выполнения.

### 4.3 Мелкое

- Флаг `minor` есть в модели и сохраняется в базе, но не влияет ни на видимость,
  ни на отображение: отдельного правила доступа для несовершеннолетних нет.
- Ключи React в галереях и списках фактов заданы индексом массива — при
  пересортировке или удалении состояние элементов смещается.
- `<family-map>` ждёт появления `window.d3` не более 12 секунд и при неудаче
  показывает общее сообщение, не различая отсутствие файла и ошибку SRI.
- Клиент не передаёт `version` карточки при правке, хотя сервер её ведёт:
  контроль конкурентных правок (ответ `409`) пока не включается.

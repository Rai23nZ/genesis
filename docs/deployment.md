# Серверная часть: решения и порядок работ

Документ объясняет **почему** контур устроен так, а не иначе. Пошаговая
установка, обслуживание и разбор неполадок — в `README.md` серверной части.

Сама серверная часть в этом репозитории не лежит: здесь код клиента и решения по
архитектуре, код сервера хранится и доставляется отдельно. Ссылки вида
`server/host/…` ниже указывают на файлы внутри неё.

Первый контур разворачивается на временном поддомене и переносится на основной
сервер по разделу 8 — скриптом, а не руками. Во всех примерах `dev.example.org`
— временный адрес, `example.org` — рабочий: настоящие домены, адреса серверов,
пароли и файлы с записями о людях в репозиторий не попадают ни при каких
условиях.

---

## 1. Что изменилось по существу

| | Было | Стало |
|---|---|---|
| Хранение | Массив в памяти вкладки | SQLite на сервере, файл на диске |
| Правки | Исчезают при `F5` | Запись в базу, очередь модерации переживает перезапуск |
| Вход | Отсутствует | Сессия на сервере: коды приглашений и пароли модераторов |
| Скрытие живущих | Фильтр в интерфейсе поверх полных данных | Сервер не кладёт эти записи в ответ |
| Признак «живущий» | Не выставлялся при импорте вообще | Правило при разборе + поимённый отчёт модератору |
| Даты GEDCOM | `14 MAR 1902` попадало в карточку как есть | Приводятся к привычной записи при разборе |
| Зависимости | unpkg и jsdelivr на каждой загрузке | Локальные копии, строгий CSP |
| Фотографии | `blob:` до закрытия вкладки | Файлы на диске, EXIF снят, выдача по правам |

## 2. Целевая архитектура

```
браузер
  └─ https://dev.example.org                 Caddy: статика + TLS
       └─ /api/*  → 127.0.0.1:8788 (Bun)
                      ├─ SQLite (WAL)  /srv/gen-tree/var/archive.sqlite
                      └─ файлы снимков  /srv/gen-tree/var/uploads/
```

Выбор продиктован тем, что машина не пустая: на ней уже работает другой сервис
за Caddy, а значит 80 и 443 заняты, зато Caddy и Bun установлены.

| Компонент | Выбор | Обоснование |
|---|---|---|
| Фронт в интернет | **Caddy** | Держит 443. nginx поднять нельзя — порт занят. Свой site-блок кладётся в `conf.d/`, чужой не трогается |
| Среда | **Bun** | Уже установлен. SQLite и argon2id встроены: ставить `sqlite3`, `argon2`, `express` не нужно |
| База | SQLite (WAL) | Один сервер, одна семья. Бэкап — копия файла, восстановление — обратная копия |
| Пароли и коды | argon2id (`Bun.password`) | Хранится только хэш; сравнения с открытым текстом нет нигде |
| Сессии | Записи в таблице + cookie | Доступ конкретного человека отзывается мгновенно, в отличие от JWT |

Бэкенд слушает `127.0.0.1` и наружу не публикуется — только через Caddy.

**Секрета для подписи сессий в конфигурации нет намеренно.** Идентификатор
сессии — 32 случайных байта, и вся власть у строки в таблице: подписывать
нечего, ротировать нечего. При переезде доступ снимается отзывом записей
(`cli/revoke-sessions.js`), а не сменой ключа.

## 3. Раскладка на диске

```
/srv/gen-tree/
├── app/                клон репозитория: статика, server/, vendor/
├── etc/
│   ├── .env            640 root:gentree — DOMAIN, PORT, DB_PATH, сроки
│   └── web/config.js   644 — apiBase для клиента, собирается из DOMAIN
└── var/
    ├── archive.sqlite  база
    ├── uploads/        файлы снимков, вне webroot
    └── backups/        ночные копии
```

Два решения ради переносимости:

1. **Всё состояние под одним корнем.** Перенос — это слепок `etc` + база;
   код берётся из репозитория, остальное собирается заново.
2. **`config.js` отдаётся из `etc/web/`, а не из клона.** Файл генерируется при
   развёртывании; лежи он в рабочей копии — конфликтовал бы при каждом
   `git pull`. Домен живёт ровно в одном месте — `DOMAIN` в `.env`.

## 4. Схема базы

`users`, `invites`, `sessions`, `people`, `relationships`, `places`,
`moderation_queue`, `settings`, `audit_log`, `login_attempts` — определения в
`server/host/db.js`, схема создаётся при открытии базы и обновляется
идемпотентно.

ФИО хранится по частям, отец и мать — колонками `father_id`/`mother_id`: у
человека их не больше одного каждого, и раскладка древа спрашивает именно их.
Супруги вынесены в `relationships` взаимной парой строк — их может быть
несколько, и связь нужна с обоих концов.

Хронология мест и записи о снимках хранятся JSON-полем `people.extra_json`:
сервер по этим спискам не фильтрует и не соединяет, это данные для отображения.

`people.version` увеличивается при каждой записи — основание для контроля
конкурентных правок. Клиент уже передаёт версию карточки в теле запроса
`POST /api/people/:id/edit` полем `version`: это версия на момент открытия
правки. Сервер должен сравнить её с текущей и ответить `409`, если карточку
успели изменить, — интерфейс этот код разбирает и объясняет словами. Пока
сервер поле игнорирует, поведение прежнее: побеждает тот, кто сохранил вторым.

## 5. Контракт API

| Метод | Маршрут | Доступ | Ответ / действие |
|---|---|---|---|
| `GET` | `/api/archive` | любой | `{ title, places, people, moderation }`. Гостю записи живущих не отдаются, ссылки на них вычищаются из `fatherId`/`motherId`/`spouseIds`; `moderation` пуст всем, кроме модератора |
| `POST` | `/api/auth/login` | любой | `{ role }` + cookie сессии. `401` при неверных данных, `429` после 5 неудач за 15 минут |
| `POST` | `/api/auth/logout` | сессия | Проставляет `revoked_at` |
| `POST` | `/api/people/:id/edit` | родственник, модератор | `{ queued: true }` родственнику, `{ queued: false }` модератору |
| `POST` | `/api/moderation/:id/approve` | модератор | Применяет патч в транзакции |
| `POST` | `/api/moderation/:id/reject` | модератор | Помечает запись отклонённой |
| `POST` | `/api/import` | модератор | GEDCOM/JSON, до 20 МБ. `dryRun: true` — разбор без записи: возвращает отчёт с числом карточек, помеченных живущими |
| `POST` | `/api/people` | родственник, модератор | Новый человек: модератору сразу, родственнику в очередь |
| `POST` | `/api/people/:id/delete` | модератор | Удаляет карточку и ссылки на неё, отклоняет её правки в очереди |
| `POST` | `/api/people/:id/photos` | родственник, модератор | Снимки в JSON (data-URL), до 12 за раз. Проверяется сигнатура файла, вырезаются EXIF и текстовые секции |
| `PATCH` | `/api/people/:id/photos` | модератор | Правка галереи: подпись, точка кадрирования `focus`, удаление по `id`. Добавить снимок может и родственник, убрать чужой из архива — нет. Файл на диске не трогается: имя файла это его sha256, и один снимок может лежать в двух карточках |
| `GET` | `/api/photos/:id` | по роли | Файл после проверки прав: снимок живущего гостю не отдаётся. `?thumb=1` — уменьшенная копия |
| `GET` | `/health` | локально | Состояние службы для проверок и мониторинга |

Правила:

1. Фильтрация по роли — до сериализации: поля живущих не попадают в JSON гостя
   даже в скрытом виде.
2. Все ответы — `Cache-Control: no-store`.
3. Роль берётся из сессии. Поля запроса, которым можно было бы объявить себя
   модератором, не существует.
4. Правка родственника очищается от полей `living` и `minor` **при приёме**, а
   не при применении: иначе запрещённое поле дожило бы в очереди до одобрения и
   применилось от имени модератора.
5. Ограничения частоты: 60 запросов в минуту на адрес на чтение, 30 на запись — модератор, разбирающий очередь, не должен упираться в ограничение.

Импорт доступен и кнопкой в интерфейсе, и из CLI — разбор с записью выполняет
один модуль `server/host/import.js`, потому что правило «живущий» решает, кого
увидит гость, и расходиться в двух реализациях оно не должно. Оба пути сначала
показывают отчёт (сколько принято, что отклонено, кто помечен живущим) и лишь
затем пишут в базу: в интерфейсе — подтверждением, в CLI — флагом `--dry-run`.

Экспорт остаётся двумя разными вещами: кнопка выгружает то, что видит текущая
роль, а `cli/export.js` — полный архив с очередью модерации.

## 6. Доступ и учётные данные

| Роль | Выдача | Срок | Хранение секрета |
|---|---|---|---|
| Владелец/модератор | `cli/create-moderator.js` на сервере | 30 дней сессия | argon2id, пароль от 12 символов |
| Родственник | `cli/invite.js`, код передаётся лично | 14 дней | argon2id от кода, одноразовый |
| Гость | Без входа | — | — |

- Cookie: `HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/`, срок равен сроку сессии.
- Смена пароля отзывает все сессии.
- Неудачные входы пишутся в `audit_log` и `login_attempts`; после 5 подряд
  адрес блокируется на 15 минут.
- Код приглашения сравнивается без учёта регистра и дефисов: его диктуют
  голосом. К паролю модератора это не относится.

## 7. Фотографии

Снимок уменьшается в браузере через canvas и уходит на сервер уже без EXIF:
canvas переносит только пиксели. Полагаться на это одно нельзя — прислать можно
что угодно, — поэтому сервер проверяет сигнатуру файла (а не расширение и не
заявленный тип) и сам вырезает секции `APPn` у JPEG, текстовые и `eXIf` у PNG,
`EXIF`/`XMP` у WebP. Отдельной библиотеки обработки изображений для этого не
нужно, а исходные пиксели не перекодируются второй раз.

Файлы лежат в `var/uploads/<первые два знака хэша>/<хэш>` — вне webroot и не
упомянуты в конфигурации Caddy. Одинаковые снимки не плодятся: имя файла есть
его хэш. Наружу уходит только адрес маршрута выдачи, путь на диске и хэш
остаются внутренним делом сервера.

Выдача — только `GET /api/photos/:id`, и право определяется человеком, которому
снимок принадлежит: карточку живущего прямой ссылкой не достать. При переезде
каталог со снимками входит в слепок `migrate.sh`: в базе лежат только имена файлов.

Синхронизация: источник истины — сервер, клиент перечитывает `/api/archive`
после входа, правки и решения модератора. Потока событий для двух модераторов
одновременно нет — второй увидит решение после следующей загрузки.

## 8. Перенос на основной сервер

Порядок рассчитан на то, что временный контур остаётся рабочим до последнего
шага и служит точкой отката.

1. `migrate.sh --out /root/cutover.tgz` — служба останавливается на время
   слепка (`VACUUM INTO`, согласованная копия) и запускается снова.
2. На новом сервере: `git clone`, затем
   `deploy.sh --restore /root/cutover.tgz --domain <новый домен>`.
3. Проверка нового контура по таблице приёмки — на его собственном адресе.
4. Переключение A-записи; TTL снизить до 300 с заранее.
5. `migrate.sh --revoke` — отзыв сессий и неиспользованных приглашений.
6. Выдача новых кодов и смена паролей модераторов. Порядок с шагом 5 важен:
   сначала отзыв, потом выдача.
7. Временный контур держится неделю как точка отката, затем его база удаляется:
   копия персональных данных не должна жить бессрочно.

Откат до шага 7 — это переключение A-записи обратно.

## 9. Резервное копирование

Ночная копия базы в 03:00 через `backup.sh` (`VACUUM INTO`, службу
останавливать не нужно), хранение 14 файлов в `var/backups/`.

Копия обязана уезжать за пределы сервера — объектное хранилище или домашний
диск. Потеря машины не должна означать потерю архива. Раз в квартал —
контрольное восстановление в отдельный каталог: копия, которую ни разу не
разворачивали, копией не является.
